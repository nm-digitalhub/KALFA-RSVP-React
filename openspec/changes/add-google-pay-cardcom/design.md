# Design

## Context

See `proposal.md` for motivation. Facts below were read in the code, measured on the live database, or read from CardCom's public material on 18.10.2026. CardCom's sample was fetched through a summarizing fetch tool, so its quotes are re-read from the raw files at apply time (task 1.1).

- **The form.** `cardcom-open-fields-form.tsx` opens a CardCom session when shown (`POST …/purchase/cardcom` returns only a `LowProfileId`), initialises the frames, and on "pay" posts `doTransaction` to the master frame. Its `message` listener (installed once a session exists) passes every event through `parseFrameMessage`, which accepts only CardCom's origin and only a string `action`; `HandleSubmit` and `HandleEror` call `settle()`, `handleValidations` for `reCaptcha` sets the captcha state. `settle()` calls `POST …/purchase/settle` up to six times, four seconds apart.
- **Settlement.** `settleCardcomSession` is the only thing that closes a CardCom payment. It asks `GetLpResult`, requires `ResponseCode 0`, the requested operation, a transaction id, a matching terminal and a matching amount and currency, and otherwise parks the row in `review`. The cardholder ID, card facts and `ExternalPaymentVector` are read defensively and never block a confirmed payment. The webhook, the buyer's call and the sweeper all end here and race safely (compare-and-set).
- **Activation.** Only the settle route activates the campaign (`activateAfterPayment`, only while the campaign is still `approved`). When the form opens and finds the session already settled (`startCardcomPurchase` → `resolvePending` → `already_paid`), it only calls `router.refresh()`; it does not call the settle route.
- **Request.** `create-request.ts` sets `SuccessRedirectUrl` and `FailedRedirectUrl` to the payment page and `UIDefinition` with the buyer's name, email and phone. It sends no `ThreeDSecureState` (reverted to the terminal's own setting, Auto, by the owner on 18.10.2026: the forced `Enabled` of commit 537b26a8, 11.10.2026, was followed by 4 of 4 real payments ending in code 5119, while the 3 real payments before it were paid).
- **CardCom's sample (public repo `CardCom/OpenFields-FrontEnd`).** The Google Pay frame is `<iframe allow="payment" id="CardComGooglePay" name="CardComGooglePay" src="https://secure.cardcom.solutions/api/openfields/GooglePay?terminalNumber=…" style="max-width:277px;height:64px">`. `setCardOwnerDetails` posts `{ action: 'setCardOwnerDetails', data: { cardOwnerName, cardOwnerEmail, cardOwnerPhone } }` to the **master** frame, called on blur of the name and email fields; the sample uses `'*'` as target and carries a comment to validate the message origin. The sample's `doTransaction` sends owner ID zeros "unless your terminal requires a valid card owner id".
- **Switch precedent.** The save-card switch (migration `20261012030027_cardcom_save_card_switch.sql`) is a column on `cardcom_config`, a parameter of the `cardcom_config_save` function, a field on `getCardcomServerConfig`, the admin form, the Zod schema, the server action and an activity-log entry.
- **Headers.** `next.config.ts` sets no `Permissions-Policy` and no CSP for the payment page (a CSP exists only on one unrelated route), so nothing in the app blocks a CardCom frame.
- **Ledger.** `provider_payment_vector` is filled from `ExternalPaymentVector` by `paymentFactsFromCardcom`; all 14 live CardCom rows (card payments and refunds) have it null.
- **Refund.** `cardcom-refund.ts` refunds by CardCom's transaction id and only carries the stored holder-ID reference forward; it does not need the holder ID to refund.

## Goals / Non-Goals

**Goals:**
- A buyer can pay with Google Pay; the payment is decided, checked and recorded exactly as a card payment, and the campaign starts.
- Nothing changes for any buyer until the owner turns the setting on, and the first exposure can be limited to platform administrators.
- The card form is unaffected when the wallet is off, unavailable or broken.

**Non-Goals:**
- Apple Pay, Bit, other wallets; the SUMIT fallback form; the owner-ID requirement of the card flow; refund logic; pricing.

## Decisions

**D1. A three-position setting on `cardcom_config`: `off | admins | all`, default `off`.**
Modeled on the save-card switch (column, `cardcom_config_save` parameter, server config field, admin form, Zod, action, activity log), with the value in the log. `admins` reuses the page's existing `mayUseTestTerminal` rule (the same people who may configure the integration), so the owner can run the real ₪1 acceptance on production without exposing any buyer. Any read problem resolves to `off`. *Alternatives rejected:* an environment flag or constant (needs a deploy, no audit trail); a plain on/off switch (testing on the real terminal would expose every buyer).

**D2. The page decides, the browser is told.** `page.tsx` computes whether the option is offered: provider is CardCom, setting allows this buyer, the save-card setting is off. It passes the form a single `googlePayTerminal` (the terminal number from the same config object that opens the session) or `null`. The browser never decides eligibility. If the configuration changes between render and session open, the existing terminal lock in settlement sends the row to review rather than guessing.

**D3. Protocol additions stay in `open-fields.ts`, pure and tested.** A typed `SetCardOwnerDetailsMessage` (its three details under both the camelCase spelling of the article and the PascalCase spelling the running scripts read, see Verified facts, task 8.2) with a builder that reuses the same name, email and phone validators as `validateCardholder` (one definition, extracted), a `googlePayFrameSrc(terminal)` that accepts only a positive integer, and the frame id constant. The new message goes to the master frame, as in the sample, never to the Google Pay frame. **Changed 18.10.2026, twice (owner instructions: "work exactly" like CardCom's documented call, then the same for `init` and `doTransaction`):** `postToFrame` posts every message — `init`, `doTransaction` and `setCardOwnerDetails` — with `'*'` as the target, exactly as CardCom's sample writes each call; the separate `postCardOwnerDetails` is gone. *The earlier rule (post only to CardCom's exact origin) is withdrawn; the cost is that, if the master frame's document were ever not CardCom's, what the buyer typed into our form (name, ID, e-mail, phone, address, city, expiry) would go to it. The card number and CVV are never in these messages: they stay in CardCom's own frames.*

**D4. When the details are sent and when the option is usable.** Sent once after the master frame loads and again whenever name, email or phone changes and all three are valid (debounced about 250 ms); and once more, per session, when CardCom's master frame says it loaded the session's settings (`initialized`), because loading them puts the session's own name and e-mail over what was sent earlier and hands the wallet frame a snapshot of that state (read in the master's source, 18.10.2026). The wallet is "ready" only after the current values were posted; any edit flips it to not-ready synchronously, so a tap can never beat the update. Not-ready is expressed with `inert` on the wrapper plus `aria-disabled` and a visible sentence naming the missing detail (the frame is cross-origin, so we cannot disable its button directly). It is also not ready while a card payment is in flight.

**D5. Markup.** The frame is rendered beside the other CardCom frames, above the card fields with an "or" divider, with exactly `id` and `name` `CardComGooglePay` (CardCom's scripts find frames by name), `allow="payment"` and `allowpaymentrequest="true"` (both, as CardCom's article asks) on this frame only, a Hebrew `title`, and CardCom's own button left unstyled. Its absence or failure cannot affect the card form because nothing in the card flow depends on it.

**D6. Result handling reuses the listener.** `HandleSubmit` / `HandleEror` from the wallet frame hit the same code path and only trigger `settle()`. One addition: when such a message arrives while the form is `ready`, the phase becomes `paying`, so the spinner shows and the card button is disabled. A buyer who somehow uses card and wallet on the same session is safe: the database allows one pending and one successful purchase per campaign, and settlement is idempotent.

**D7. Redirect return calls the settle route.** In the form's open-session handling, `already_paid` now calls the settle route once (without `submitted`) and handles its answer like `settle()` does (paid → replace the URL with `?paid=1`, refresh), instead of only refreshing. The route starts the campaign only if it is still `approved`, so a campaign already started by the webhook is not started twice. This branch is reached only when the ledger was `pending` at render and paid by session open, which is exactly the return case; a ledger already `collected` does not render the form. This also repairs the same gap for a 3D Secure redirect. *Alternative rejected:* activating inside `startCardcomPurchase`; that function opens sessions and runs without the buyer-facing activation rules.

**D8. Withheld while the card must be saved.** If `save_card_on_purchase` is on, the session asks for `ChargeAndCreateToken`, and settlement parks a confirmed charge without a token in `review`. Whether a wallet payment returns a token is unverified, so the option is not offered in that state (fail-safe). Lifting this needs a measured answer and its own change.

**D9. Channel visibility.** `paymentFactsFromCardcom` already keeps `ExternalPaymentVector` when it is a string (CardCom sent `_3DS` on 11.10.2026), and the ledger already has the column; no real payment has happened since the code shipped, which is why every live row is null (see Verified facts, task 1.5). The extractor is not changed. Synthetic fixtures prove that a wallet-shaped answer, with the channel as a string such as `GooglePay`, lands in `provider_payment_vector` and still goes through the same amount, currency and terminal checks; a value of another type stays null, as the existing test says. Payment review shows the stored value, labeled by values actually observed and raw when unmapped. The first real wallet payment records the exact spelling CardCom uses.

**D10. No header or CSP change.** `allow="payment"` on the one frame is enough; if a CSP is added to this page later it must allow CardCom's origin for frames and scripts, as the card frames already need.

**D12. 3D Secure is CardCom's, so the page's job is to host it correctly and to tell the truth.** Read on 18.10.2026 in CardCom's own scripts (`3DS.js`, and the master frame's `OpenFields.js?v=5.0.9784.18617`): when the bank needs a check, the master frame posts `StartDeviceFingerPrint` or `CardHolderChallenge` to the page, `3DS.js` (which must be loaded in the page) opens the bank's hidden device-check frame (waiting about 11 s for the issuer) or its challenge window, and the result goes back to the master frame. Errors come as `HandleEror` with a numeric `ResponseCode`: 408 = the device check timed out, 333 = refused or failed, 400 = an invalid detail. Three consequences: (1) `3DS.js` is loaded when the form is shown, before any frame, as CardCom's sample does in `<head>`, because the master frame asks the page for the screen's size the moment it initialises; (2) the form shows the step the bank is on; (3) a settled-as-declined session after code 408 or 333 is told as "the bank's check did not complete", not as a declined card (the old sentence sent a buyer to retype a card that was fine). The server's decision is unchanged. *Alternative rejected:* passing the screen size in the `init` message, which relies on fields CardCom does not document (the master frame's own source does read `screenWidth`, `screenHeight` and `screenColorDepth` from `init`, but `3DS.js` answers its request for them, so it was not needed). *Added 18.10.2026 (owner approved):* code `333` is posted from several branches of the master frame and only its Hebrew sentence tells them apart (`3DS אימות נכשל`, `3DS שגיאת אימות`, `שגיאה כללית`; `408` has its own), so the page maps those four exact sentences to labels (`fail_auth`, `auth_error`, `general_error`, `timeout`; any other text is dropped) and, when it asks the server to settle after an error, sends the code, the last step and the label. `settleCardcomSession` appends them to the note of a row it closes as failed, worded as the browser's report. The route accepts only numbers and those labels and only with `submitted`; nothing in it is read to decide the outcome. *Alternative rejected:* storing CardCom's sentence as received (free text from a third party in the ledger).

**D13. A new session for every opening of the form (owner approved 18.10.2026).** `resolvePending` used to hand back a young unpaid session (a reload, a second tab or device), which CardCom's guide forbids ("each time you submit a payment form, create a new LowProfile"). The one Google Pay attempt of the day that stopped on its return from Google ran on such a reused, 16-minute-old session; the two on fresh sessions went on (a correlation of three, not a proof). Now the pending session is settled with `finalizeUnpaid` and `replacedByNewSession`: paid → `already_paid`; not paid → closed as failed with a note that says it was replaced and no "declined" alert (nothing was declined), and a new session opens; unreadable → `in_progress`. The database still allows one pending row per campaign and kind, so the old one must close before the new one is written. *Cost:* a buyer with two tabs open who pays in the older one pays on a session whose row is already closed; that is the existing "payment after failure" case, which alerts staff for a manual match. *Alternative rejected:* keeping the resume and only replacing sessions older than a few minutes, which keeps the deviation.

## Risks / Trade-offs

- **Terminal not enabled or needs registration (gate).** The frame may render an error or nothing. → Setting stays `off` until CardCom confirms enablement and any domain or merchant registration (task 1.2); first exposure is `admins`.
- **Unknown requirements of the wallet path.** Whether reCAPTCHA, the owner ID, or the address apply to a wallet payment, and which receipt is produced, is undocumented. → Task 1.3 asks CardCom and the first real ₪1 run records the observed answer; the spec makes no promise beyond "same checks as a card".
- **A closed table grants `UPDATE` per column.** `cardcom_config` gives `service_role` `SELECT` and `INSERT` on the table and `UPDATE` only on six named columns (migration `20261007215705`), so a new column is read-only to the application until it is granted. The setting's migration added `google_pay_mode` without the grant, and the save-card migration of 12.10 had done the same for its column: every save through the admin form failed with 42501 until `20261018072228` grants both. Reads were unaffected. The first verification ran the function as the migration's own role and so could not see it. → Every migration that adds a column to a closed table is also verified as `service_role`, with the application's own call; the form's save now logs the database error code (never the message) instead of failing silently.
- **Refunds failed once.** 5 of 6 real CardCom refunds failed, all on 9.10.2026; the cause is a permission on the CardCom API user (see Verified facts, task 1.4), and the last attempt succeeded. → One success is a thin sample: the real acceptance includes a refund, and the owner confirms the permission is permanent.
- **Listener checks origin only.** The 7.10 plan says origin and `event.source`; the code checks origin only. CardCom's 3D Secure may run in another CardCom window, so adding a source check could break it. → Not changed here; recorded, and the new frame adds no new origin.
- **`inert` as a gate.** A user could in principle focus the frame by other means. → Settlement does not trust the browser; a payment without valid details is a CardCom-side decline at worst, and nothing is recorded paid without CardCom's confirmation.
- **Device and browser coverage unknown.** Google Pay inside an iframe depends on browser support. → Real-device checks (task 6.3); the card form is always available.
- **A sample fetched through a summarizer.** → Raw files re-read before apply.

## Migration Plan

1. Gates cleared (CardCom enablement, wallet requirements, refund investigation).
2. Migration: add `cardcom_config.google_pay_mode` (check constraint, default `off`) and extend `cardcom_config_save`; the owner pushes it; types regenerated with the project script.
3. Code behind the setting, tests, lint, typecheck, build.
4. Deploy with the setting at `off`. No buyer sees a change.
5. Owner sets `admins`, runs a real ₪1 wallet payment and its refund on the real terminal, each run approved; results recorded in the apply report.
6. Only after a clean run and an answer on the failed refunds, the owner decides `all`.

**Rollback:** set the setting to `off` (immediate, no deploy). Code rollback is a normal revert; the column can stay.

**Task 1.4, 18.10.2026 (live ledger, status codes and notes only).** There are six real CardCom refund rows, all recorded on 9.10.2026 between 11:36 and 14:40, all of a ₪1 purchase that had succeeded, all on the live terminal. No refund has been attempted since, so one success is the whole evidence that refunds now work. The owner confirms the permission is permanent (open for the owner, see the report).

**Task 1.5, 18.10.2026 (corrected the same day).** The channel is null on the three real succeeded purchases because they all predate the code that keeps it: the purchases were recorded on 8.10 18:18, 11.10 15:01 and 11.10 15:12, the column's migration is `20261011151634` (11.10, about 15:16) and the commit that reads `ExternalPaymentVector` is `d5932905` (11.10 18:23). **Tasks 1.2 and 1.3, 18.10.2026 (CardCom's terminal article and the owner's screen).** The owner supplied a screenshot of CardCom's terminal editor for terminal 172204 with the dialog "הפעלת GooglePay למסוף 172204" open and its "פעיל" box ticked (whether "השינויים נשמרו" appeared is for the owner to confirm), plus CardCom's own article for the setting. From the article:
- **Enablement:** available on any terminal defined as an internet terminal; if the terminal is not suitable the setting is refused and the owner is told to contact support. (The three real purchases carry entry mode `Internet`, which fits.)
- **Supported:** charge only; charge and create token "when the charge is actually made through overriding settings" (unclear for the Open Fields frame, so D8 stands); ILS, USD and EUR; **one payment only** (our `numberOfPayments` is `1`); design version 5 for landing pages.
- **Not supported:** installments, a Google Pay button outside a CardCom payment page, standing orders.

- **Still not answered:** whether reCAPTCHA, the cardholder ID or the address are required for a wallet payment, which receipt is produced, and whether a token comes back; these remain for the first real wallet run.

**3D Secure, 18.10.2026 (CardCom's scripts read as downloaded files).** An error seen in the owner's browser, `Cannot read properties of null (reading 'ResponseCode')` in `DeviceFingerPrint3DSecureFunc`, is a fault in CardCom's code: when the bank's device check does not answer within ~11 s, `3DS.js` calls `DeviceFingerPrintFail`; if CardCom's server answers JSON `null`, `3DS.js` forwards `ThreeDSecureDeviceFingerprintResult_null` and the master frame reads `.ResponseCode` of `null`. The branch that handles a failed request builds a proper object; the `null` branch has no guard. The owner's two attempts that day ended as failed with CardCom code `5119` ("pending or not completed") and nothing was charged. The owner's browser reached the site from a Google LLC address (`34.165.228.5`), a datacenter range, where banks' 3D Secure pages often do not answer; that this is the cause is an inference. The 3D Secure path itself has not been run to success: it needs a real card and the real terminal (the test terminal is closed to customers), so it is task 8.3.

**Task 8.2, 18.10.2026 (every CardCom script that runs on the page, read as downloaded files).** Versions read: the master page loads `OpenFields.js?v=5.0.9784.18617` (113,748 bytes with its `state.js` and `types.js` modules), the Google Pay frame loads `GooglePay.js?v=5.0.9784.18617` (12,982 bytes), and `3DS.js` is 6,922 bytes. Findings:
- **Key spelling of `setCardOwnerDetails` (a real defect, fixed).** The article and CardCom's public sample write the details camelCase (`cardOwnerName`, `cardOwnerEmail`, `cardOwnerPhone`), but both running scripts read them PascalCase: the master frame's `setCardOwnerDetails` takes `details.CardOwnerName / CardOwnerEmail / CardOwnerPhone` (its typed `CardOwnerDetails` is PascalCase) and forwards the object to the Google Pay frame, whose `setCardOwnerDetails` reads `data.CardOwnerName / CardOwnerEmail / CardOwnerPhone`. Sent camelCase alone, the master stored `undefined` and the wallet never received an edited name, e-mail or phone. The message now carries both spellings (D3).
- **Address and city (a real defect, fixed).** The master frame reads `address`, `city` and `zipCode` from the TOP LEVEL of `doTransaction` (its typed `SubmitPaymentRequest` lists them and has no `document`) and never reads a `document` object, so what the buyer typed there reached CardCom nowhere. They are now sent at the top level; `document` stays because the sample sends it. Plan item U13 ("is `document` read") is answered: it is not, by the master frame.
- **3D Secure result codes.** `Cardcom3DSecureResponseCode`: PassOver3DSecureAuth −1, Unknown 0, Auth 1, FingerPrint 2, CardHolderChellenge 3, FailAuth 4, FailError 5, RejectAuth 6. `333` is posted for FailAuth, RejectAuth, FailError (when it is not the page's own timeout) and for any unknown code, after the initial answer, after the device check and after the challenge; the page's own 11-second timeout is `408`. A `333` that arrives about 4 seconds after `StartDeviceFingerPrint` is therefore a real answer of CardCom's 3D Secure server, not a timeout.
- **What the page must send to start 3D Secure** is only what CardCom's scripts build themselves: the card, `cardOwnerName/Email/Phone` (3D Secure needs the phone or the email), the amount, and browser values (`GetScreenValues` answered by `3DS.js`, the browser's language and timezone from the master frame's own state). Nothing else is expected from the page.
- **Correction to the note above.** The inference that the owner's failures were caused by reaching the site from a datacenter address is withdrawn: the same refusal (`333`, then CardCom code `5119`, nothing charged) happened from a phone on an Israeli mobile network and on the owner's desktop, with the forced-3DS request field removed and with it present. The cause is not in what the page sends; CardCom was asked (task 8.4).
