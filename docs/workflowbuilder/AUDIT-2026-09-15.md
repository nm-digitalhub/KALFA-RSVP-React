## 6. ✅ תוקן: revalidation לא מאפס עוד את מצב הריצה

### הבעיה שנמדדה

במצב הקודם `workflow-editor.tsx` שילב באותו effect שתי אחריויות שונות: hydration של `globalVariables` ומצב lifecycle מקומי של ביקור בעורך (`resetExecution()` ו־`resetPanels()`). מערך התלויות היה `[workflowId, initialGlobalVariables]`.

RSC revalidation עשוי לשחזר את `initialGlobalVariables` בזהות אובייקט חדשה גם כאשר נשארים באותו workflow. לכן לא נכון לקשור את lifecycle המקומי לזהות של prop שמגיע מהשרת: שינוי כזה היה עלול להפעיל את cleanup ואת גוף ה־effect ולאפס את מצב הריצה והפאנלים ללא החלפת workflow.

ה־hydration הידני של `globalVariables` עצמו נדרש. בבדיקת החבילה המותקנת `@workflowbuilder/sdk@2.3.0` נמצא שה־Root הציבורי חושף `initialNodes` ו־`initialEdges`, אך אינו חושף `initialGlobalVariables`. לעומת זאת, שכבת ה־integration הפנימית ו־`IntegrationDataFormat` כן כוללות `globalVariables`, ונתוני השמירה של ה־SDK כוללים אותם. לא נמצא export ציבורי של `setStoreGlobalVariables`.

### התיקון שיושם

```ts
useEffect(() => {
  useStore.setState({ globalVariables: initialGlobalVariables ?? {} });
}, [initialGlobalVariables]);

useEffect(() => {
  resetExecution();
  resetPanels();

  return () => {
    resetExecution();
    resetPanels();
  };
}, [workflowId]);
```

כך שינוי ב־`globalVariables` ממשיך להסתנכרן אל store של ה־SDK, בעוד reconstruction של server props באותו workflow אינו מאפס את execution/panel lifecycle. החלפת workflow עדיין מפעילה reset דרך `[workflowId]`, ו־`key={workflow.id}` גורם ל־remount בעת החלפת workflow.

### אימות regression

נוסף guard ממוקד ב־`workflow-editor-lifecycle.test.ts`. בוצע fault injection מבוקר: במצב המתוקן שתי הבדיקות עברו; החזרת `initialGlobalVariables` למערך התלויות של lifecycle effect גרמה בדיוק לבדיקת ה־regression להיכשל בעוד הבדיקה השנייה נשארה עוברת; לאחר restore שתי הבדיקות חזרו לעבור.

נוסף גם invariant ב־`sdk-integration-invariants.test.ts`: `WorkflowBuilderRootProps` אינו חושף `initialGlobalVariables`, `IntegrationDataFormat` כן כולל `globalVariables`, וה־public index אינו מייצא `setStoreGlobalVariables`.

### נתוני DB שנמדדו לפני התיקון

בזמן האבחון היו 20 workflows; ב־7 מהם כבר היה המפתח `globalVariables`, וכל שבעת הערכים היו `{}`. ארבעת ה־workflows החמושים היו בין השבעה. זהו snapshot היסטורי מלפני התיקון ואינו טענה לגבי מצב ה־DB לאחריו.

## 9. ✅ תוקן: נרמול legacy `status` של `action.update_guest_status`

### הבעיה שנמדדה

ב־DB נמצאו שני צמתים קיימים מסוג `action.update_guest_status` שבהם ערך ה־RSVP הישן נשמר ב־`status` (`attending` / `declined`) ולא היה `rsvpStatus`. במקביל, `status` משמש כיום את מחזור־החיים של צומת ה־SDK (`active` / `draft` / `disabled`). לכן ה־JSON Schema דרש `rsvpStatus`, סימן את הצמתים כשגויים, ובורר מצב הצעד קיבל ערך שאינו שייך למחזור־החיים.

ה־handler כבר תמך ב־legacy alias דרך `LEGACY_PROPERTY_ALIASES`, אבל זה לא הספיק ל־SDK validator ול־UI משום שהנתונים עצמם נשארו בצורה הישנה.

### התיקון שיושם

`normalize-legacy-properties.ts` כולל כעת migration ממוקד עבור `action.update_guest_status`. כאשר `rsvpStatus` אינו קיים ו־`status` הוא אחד מערכי ה־RSVP החוקיים (`attending`, `declined`, `maybe`), ה־normalizer מעביר את הערך ל־`rsvpStatus` ומגדיר את `status` ל־`active`, כדי להחזיר את השדה לבעלות מחזור־החיים של ה־SDK.

המעבר מכוון ולא migration גנרי של כל alias: הוא אינו מפרש `active` / `draft` / `disabled` כ־RSVP, אינו מחליף `rsvpStatus` קיים, ואינו נוגע ב־node types אחרים. ה־normalizer נשאר idempotent.

### אימות

`normalize-legacy-properties.test.ts` מכסה את ה־legacy collision ואת גבולות התיקון, לרבות תיקון pre-lifecycle RSVP status, מעבר schema לאחר התיקון, אי־פירוש lifecycle status כ־RSVP, precedence ל־`rsvpStatus` הנוכחי, אי־החלת ה־alias על node type אחר ו־idempotency. אותו קובץ מכסה גם את תיקוני array/object והמרת numeric strings. בסך הכול 19 הבדיקות הממוקדות עברו.

### נתוני DB שנמדדו לפני התיקון

שני הצמתים עם `status=attending/declined`, ללא `rsvpStatus`, והשגיאות השמורות מסוג `required` הם snapshot היסטורי ששימש להוכחת ה־legacy collision. התיקון הוא normalization בעת כניסת workflow לעורך; אין להסיק מה־snapshot הישן שהשורות כבר נשמרו מחדש ב־DB לאחר התיקון.

## 10. תיקון לממצא סוכן: דחיית `secrets` — הסיכון הפוך ממה שדווח

דווח כי איבוד ענף ה־`deferSecrets` ב־re-sync עתידי יגרום לכך ש"סודות יתחילו
להיפתר אל ה־step ledger, ושום דבר לא ייכשל". **נמדד שזה לא נכון.**

`resolveNamespace` (`resolve-template.ts:138-156`) מכיר ארבעה namespaces בלבד —
`nodes`, `trigger`, `variables`, `global` — וה־`default` **זורק**:

```ts
default: {
  throw new Error(`Unresolved template reference: ${match} (unknown namespace "${namespace}")`);
}
```

אין ל־`resolveTemplate` שום גישה לסודות, בשום מסלול. הדחייה
(`resolve-template.ts:129`) היא **pass-through** — היא מחזירה את ה־match כמות
שהוא כדי ששכבה מאוחרת יותר, שמודעת לסודות, תחליף אותו.

לכן איבוד הענף במיזוג גורם ל־**זריקה רועשת** (`PermanentNodeExecutionError`)
בשורות ה־header של `action.webhook`, לא לדליפה שקטה. זו רגרסיה אמיתית — הצעד
יפסיק לעבוד — אבל היא **בטוחה ונראית לעין**, וההפך ממה שדווח.

ההגנה עצמה מתועדת נכון בקובץ (`resolve-template.ts:93-105`): ברירת המחדל היא
`off`, opt-in לכל שדה בנפרד, וכיום קורא אחד בלבד — שורות ה־header של
`action.webhook`. `references.test.ts` מצמיד את הנימוק.

## 11. נימוק שהתיישן וסותר את עצמו — וחוסם שיקול עתידי

**נמדד.** בלוק הערה אחד ב־`schemas.ts` מכיל שני תבליטים שסותרים זה את זה:

`schemas.ts:2102-2107` (תבליט ראשון):

> from the uischema. Their branch conditions are `{x, y, comparisonOperator}`

`schemas.ts:2108-2113` (התבליט הבא, שש שורות מתחת):
> "That held only while `resolve-template.ts` was unvendored; **it is vendored

התבליט השני מתקן את עצמו בנוגע ל־`outputSchema` — ובדרך מפיל את ההנחה
שהתבליט הראשון עדיין נשען עליה.

**ההוכחה שהחסם באמת נעלם:** `logic.switch` כבר חושף את הפקד המובנה —
`schemas.ts:896`: `{ type: 'DecisionBranches', scope: switchScope('properties.decisionBranches') }`.

**ותיקון עובדתי בתוך התבליט:** הוא מנמק את היעדר `DecisionBranches`, אך זה
הפקד של צומת **Decision** (`docs/workflowbuilder/nodes/decision.md:103-105`).
צומת **Conditional** של הספק משתמש ב־`DynamicConditions` על `conditionsArray`
(`docs/workflowbuilder/nodes/conditional.md:76-79`). התבליט מתאר צומת אחד
ומצדיק אחר.

### ההכרעה: פער אמיתי, אך פיצ'ר — לא חוב

`logic.condition` תומך היום ב**השוואה אחת בלבד** (`ConditionConfig` —
`types.ts:375-390`), כלומר אי אפשר לבטא "A AND B". הפקד המובנה
`DynamicConditions` עושה בדיוק את זה, והמעריך למערך תנאים עם AND/OR **כבר
בנוי** ומשרת את `logic.switch`. מה שעוצר אינו הפקד אלא **הגירת סכימה
מאוחסנת**: כל תרשים שמור נושא `field`/`operator`/`value`.

**פעולה מיידית וחסרת סיכון:** לתקן את ההערה. כל עוד הנימוק השקרי עומד, הוא
ימנע מכל קורא עתידי לשקול את ההרחבה.

## 14. מה טרם אומת, ומה עדיין פתוח

**טרם אומת בדפדפן.** סעיפים 6, 9 ו־13 מבוססים על שרשרת קוד + נתוני DB מדודים,
אבל אף אחד מהסימפטומים לא נצפה במסך חי. זה בדיוק הפער שהפרויקט כבר מכיר
(`verification-gate-runtime`): שערים סטטיים אינם רואים גבול לקוח/שרת. הצעד הזול
הוא לפתוח תהליך חמוש, ללחוץ "הצגה על הקנבס", ואז ללחוץ "ביטול" על הרצה כלשהי
ולראות אם הכפתור קופץ בחזרה.

**היקף שהוחרג במפורש.** `docs/workflowbuilder/workflowbuilder.io-md/` (75 קבצים,
1.8MB) — אתר שיווק: blog, pricing, case-study, contact, compare, consulting.
ההחרגה **נמדדה ולא הונחה**: `llms-ctx.txt` (808KB, התמצית הגדולה ביותר שם)
מכיל **אפס** מופעים של `getStoreDataForIntegration`, `useWorkflowBuilderActions`
או `customErrors`. אין שם תוכן API.

**עדיין ממתין.** הכרעת Flow Runner מול `execution-core/` (השאלה: האם הוא יודע
suspend/resume מעבר לגבול תהליך — `logic.wait` וה־handshake הקולי ממתינים שעות),
והשלמת הממצא על ארבעה פקדים שמציגים תווית באנגלית בפאנל עברי.

## 15. הכרעה: Flow Runner **אינו** המנגנון שעקפנו

השאלה הייתה אם `execution-core/` שלנו משכפל תוסף Enterprise. **נמדד שלא, ובאופן
חד־משמעי.**

`docs/workflowbuilder/overview.md:41`:
> "Workflow Builder focuses **exclusively on the frontend editor layer**. The SDK
> outputs workflow definitions as JSON that your own backend consumes and
> executes. **For in-editor execution**, the optional Flow Runner plugin
> (Enterprise) can traverse the workflow graph and run node functions directly."

`docs/workflowbuilder/plugins/flow-runner.md:11`:
> "Reference implementation of a JSON parser that turns a diagram into an
> **executable flow function**."

`:17` — מה שהוא באמת מספק: *"play / pause / stop controls in the app bar, a
visual debugger …, and a set of **demo** palette items"*.
`:23` — איך הוא מגדיר את עצמו: *"Use as a **starting point** for a production

מחזירה התאמה אחת — כפתור ה־`pause` ב־UI.

**זה מכריע עבורנו**: `logic.wait` וה־handshake של ה־callback הקולי ממתינים
**שעות** לאירוע חיצוני, עם pg-boss, lease ו־CAS. פונקציה סינכרונית אינה יכולה

> "Community Edition (Apache 2.0) already includes the visual workflow editor,

ובאותו עמוד, פעמיים, הפריט מתומחר בשמו המדויק (`:51`, `:221`):
**"Flow Runner plugin (graph traversal helper)"** — עוזר־מעבר־על־גרף.

**מסקנה:** 6,990 אירו לא היו מחליפים ולו שורה אחת מ־`execution-core/`. הם היו
