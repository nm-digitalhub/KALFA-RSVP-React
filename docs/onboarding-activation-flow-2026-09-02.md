## מה השתנה

- **שלב אחד פחות**: אחרי תפיסת מסגרת מאושרת הקמפיין מופעל אוטומטית (`src/app/api/campaigns/[id]/authorize/route.ts` → `activateCampaign`). כשל בהפעלה לא פוגע בתפיסה — הלקוח נשאר באותו עמוד עם כפתור "הפעלת הקמפיין עכשיו" (`payment/activate-now-form.tsx`). ההפעלה נרשמת ב-`activity_log` (`campaign.activated`).
- **"פרסום האירוע" נעלם כמונח**: המעבר `draft → active` נשאר (הטריגרים `events_guard_update`, `campaigns_require_active_event` לא השתנו) אבל נקרא "אישור פרטי האירוע והמשך", מציג את אזהרת הנעילה **לפני** הלחיצה, ומשורשר ליצירת הקמפיין ולהסכם (`setupCampaignAction`: publish-if-draft → createCampaign → `/approve`). `publishEventAction` הוסר.
- **עמוד הקמה**: `events/[id]/setup-steps.tsx` על גבי המודל הטהור `src/lib/data/setup-steps.ts` — שישה שלבים, בדיוק אחד `current`, פעולה אחת לשלב. שלב "הוספת מוזמנים" הוא **רך** (המלצה, לא שער — החלטת בעלים 26.7). `campaign-section.tsx` נמחק; `event-status-actions.tsx` מציג רק "סגירת האירוע".
- **שני מצבים מוצגים**: מצב האירוע (`טיוטה` / `פרטי האירוע אושרו` / `הסתיים` / `בוטל` — `eventStatusLabel`) ומצב הקמפיין **הנגזר** (`campaignStage`: `טרם הוגדר` / `ממתין לחתימה` / `ממתין לתשלום` / `ממתין להפעלה` / `פעיל` / `מושהה` / `נסגר` / `בוטל`). אין ערך enum חדש.
- **ניסוחים**: "חתימה והמשך לאמצעי תשלום"; "ההסכם נחתם בהצלחה. כעת יש להשלים אמצעי תשלום."; `EVENT_NOT_CONFIRMED_ERROR` ("יש לאשר את פרטי האירוע…") במקום "יש לפרסם…"; מסכת טלפון `050***4567` (`maskPhoneForDisplay`).
- **עמוד התשלום**: סיכום מפורש (דמי הפעלה / כלולים / מעבר לכך / אנשי קשר ברשימה / סכום התפיסה כעת / תקרה / מתי החיוב / מה אם אף אחד לא משיב) — כל מספר מה-snapshot של הקמפיין או מ-`previewCampaignHoldSizing` (קריאה בלבד, אותו נתיב חישוב כמו `prepareCampaignHold`). איור הכרטיס מוסתר בנייד. אחרי הפעלה: מסך הצלחה עם "הוספת מוזמנים" / "מעבר לניהול הקמפיין".
- **עמוד הניהול**: מצב ריק "אין עדיין מוזמנים בקמפיין" (ייבוא / הוספה / וואטסאפ) כשה-set ריק אחרי תפיסה; "דמי הפעלה" במקום "חיוב מצטבר" כש-reached=0; באנר למוזמנים שלא נכללו (מכסה מלאה); כפתור ההפעלה דורש תפיסה מאושרת (אחרת קישור לאמצעי תשלום).
- **לוח בקרה**: 0 אירועים → הפניה ל-`/app/events/new`; "אירועים שאושרו" במקום "פעילים".
- **סקירת ייבוא מוואטסאפ**: מוני "תקינות/שגויות", רשימת השורות השגויות (מתקפלת), הסבר מה עושה "אישור ייבוא".

## תיקון DB (חי מ-2.9.2026 09:33, מיגרציה `20260902062917`)

`funded_cap` בשני ה-RPC — `reconcile_authorized_set` **ו**-`try_record_billed_result` — לא יורד מתחת ל-`included_reached`:
`least(greatest(max_contacts, included), included + floor(max(0, auth − base)/price))`.
סיבה: `max_contacts` נשמר ברגע התפיסה; תפיסה עם 0 מוזמנים נתנה cap 0 — קמפיין "פעיל" שלא מקבל מוזמנים ולא מחייב תשובות. קמפיין חי אחד (אירוע QA) היה במצב הזה. legacy (0/0) ללא שינוי.

## מה נשאר כמו שהיה (בכוונה)

- ה-set הדינמי (snapshot בתפיסה + `reconcile_authorized_set` חי מ-21.7) ונתיב השליחה (`sendable-contacts.ts` INNER JOIN). זו **לא** הקפאה קשיחה: מוזמנים מאוחרים נכנסים עד `funded_cap`.

- כל שומרי L1/R9 בתוך `activateCampaign`; אף route לא כותב `campaigns.status`.

## פתוח

- **G1**: תפיסה עם רשימה קטנה מ-`included` = תקרה ₪200 לצמיתות (הכנסה, לא סיכון ללקוח). כרגע שער רך + אזהרה בעמוד התשלום; הגדלת מסגרת (top-up) = תוכנית נפרדת.
- **G3 (משפטי)**: ההסכם (`template.ts:260`) מתאר גביית דמי הפעלה "במועד הפעלת הקמפיין"; הקוד גובה בסגירה. §5 (חלון ביטול "שני ימים לפני ההפעלה") — עם הפעלה אוטומטית ההפעלה = רגע התפיסה. ל-`israeli-compliance-advisor` **לפני deploy**.
- קמפיין `pending_approval` שננטש נועל שדות וחוסם סגירת אירוע (R7); ביטול = אדמין בלבד (קיים גם לפני השינוי).
- תיקון שורה בסקירת הייבוא (§8) — תוכנית נפרדת.
- שני אינדקסים UNIQUE זהים על `campaigns(event_id) where status<>'cancelled'`; ערכי enum ללא כותב (`draft`, `scheduled`, `awaiting_invoice`, `billed`, `paid`) — ניקוי בתוכנית נפרדת.
- הקטנה (ולא הסתרה) של איור הכרטיס בנייד — לפי בדיקה ויזואלית.
