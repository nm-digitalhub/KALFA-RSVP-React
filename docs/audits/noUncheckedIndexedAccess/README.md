תאריך: 2026-10-28. מקור: [noUncheckedIndexedAccess.md](../../../noUncheckedIndexedAccess.md).

## מסקנה והיקף

הפעלת `noUncheckedIndexedAccess` במצב הקוד שנבדק מפיקה **1,872 הופעות של אבחנות ב־346 קבצים**, ובהן **1,861 אבחנות ייחודיות**. בדיקת TypeScript באותה תצורה ללא הדגל הסתיימה בהצלחה. שחזור עם הדגל הפיק פלט זהה לקובץ המצורף, בתים מול בתים. אלה אבחנות קומפילציה; מספרן אינו מספר הבאגים או מספר התיקונים הנדרשים.

המשימה שבוצעה היא מיפוי, ניתוח ותיעוד. לא תוקנו קוד, בדיקות או הגדרות, ולא הופעל הדגל באופן קבוע. נכתבו רק מסמכי הדוח בתיקייה זו. אין כאן מימוש של שינוי OpenSpec או אישור לפריסה.

## שחזור ומקור הנתונים

גרסאות שאומתו מתוך החבילות המותקנות: TypeScript **6.0.3**, Next.js **16.4.3**, Vitest **5.0.4**.

קריאת התצורה באמצעות TypeScript הראתה: `strict: true`, `skipLibCheck: true`, `incremental: true`, והדגל `noUncheckedIndexedAccess` אינו מופעל. רשימת קובצי השורש שהתקבלה מפענוח `tsconfig.typecheck.json` כוללת 2,549 קבצים; זה אינו מספר כל תלויות תוכנית TypeScript. כל 346 קובצי המקור שהוזכרו בפלט נמצאו בדיסק.

שתי הפקודות הבאות הורצו בזו אחר זו, עם הקומפיילר המקומי. `--incremental false` מנע כתיבת cache; `--pretty false` קיבע פלט טקסט רגיל.

```bash
./node_modules/.bin/tsc --noEmit -p tsconfig.typecheck.json --incremental false --pretty false
./node_modules/.bin/tsc --noEmit -p tsconfig.typecheck.json --noUncheckedIndexedAccess --incremental false --pretty false
```

## משמעות הדגל וגישת התיקון

הדגל מוסיף אפשרות `undefined` לקריאות דרך מפתחות שאינם מובטחים בטיפוס. תיעוד TypeScript הרשמי מדגים זאת ב־index signatures. [תיעוד noUncheckedIndexedAccess](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html).

בקוד שנבדק הדבר מתבטא גם בגישה למערכים, פירוק תוצאות `split`/regex, קריאת `mock.calls`, ומפות `Record<string, T>`. לעיתים בדיקת אורך קיימת או בניית מערך קבוע מבטיחות איבר בזמן ריצה, אך טיפוס הגישה עדיין כולל `undefined`. לעיתים אין הבטחה כזו, וצריך להגדיר מה לעשות כשהאיבר חסר. ההבחנה חייבת להיקבע לפי מסלול הנתונים והחוזה של הפונקציה.

עקרונות ליישום עתידי:

1. כשחוסר הוא מצב תקין: להחזיר תוצאת empty/not-found או fallback שיש לו משמעות עסקית מפורשת.
2. כשחוסר מפר חוזה: guard עם שגיאה ממוקדת, או טיפוס שמבטא את החוזה ומאומת בגבול שבו הנתונים נכנסים.
3. כשאוסף קבוע איבד מידע טיפוסי: לשמר tuple או קבוצת מפתחות סגורה, ולהימנע מהרחבה לא נחוצה ל־`T[]`/`Record<string, T>`.
4. בבדיקות: assertion שבודק קיום ומצר את הטיפוס, תוך שמירה על בדיקות מספר הקריאות והארגומנטים. שיפור helper משותף עשוי להסיר אבחנות רבות בצרכנים.
5. להימנע מתיקון גורף באמצעות `!`, `as`, `any`, דילוג על בדיקות או הוספת `?? 0`/`?? ''` ללא חוזה מתאים. ברכיבי הרשאות ותשלומים יש לשמר את סיבת הכשל ואת הטיפול הקיים במצב ריק.

## שיטת מיפוי וגבולות הביטחון

הספירה מזהה רק שורות תחילת אבחנה באמצעות:

```regex
^(.*?)\((\d+),(\d+)\): error TS(\d+): (.*)
```

שורות המשך משויכות לאבחנה הקודמת עד תחילת האבחנה הבאה. מפתח הייחודיות הוא `(file, line, column, code, first-line message)`; שני מיקומים באותה שורה אינם כפילות. כל 2,195 שורות הפלט הן כותרות אבחנות או המשכן. אינדקס הקבצים והרישום המלא נוצרו מאותו פענוח, כדי למנוע נשירת קבצים בעת חלוקת העבודה.

דוחות המומחים משלבים קריאה של מיקומי המקור עם ניתוח דפוסים וחוזים. המיפוי מכסה את כל הפלט; אין כאן הוכחה פורמלית לכל ערך אפשרי, סריקה מלאה של כל שרשרת קוראים, או תצפית על תקלה בייצור. חשד לפער בחוזה מסומן כהמלצה לבדיקה, בנפרד מ־invariant שנראה בקוד.

מקור התיעוד המקומי של Next.js שנקרא: `node_modules/next/dist/docs/01-app/03-api-reference/05-config/02-typescript.md`. הגדרות הפרויקט נבדקו ב־`tsconfig.json`, `tsconfig.typecheck.json` ו־`package.json`. תוצאת baseline מוצלחת מתייחסת לפקודת `tsc` המתועדת לעיל בלבד.
