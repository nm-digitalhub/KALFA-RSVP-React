# תוכנית: צמתי SUMIT ב-Workflows

**סטטוס: תוכנית בלבד. לא בוצע שום שינוי קוד.**
נכתב 2026-09-22. כל עובדה כאן נמדדה מהקוד או מה-DB החי — אין כאן הנחות.

---

## §0. ההחלטה שקובעת את כל המבנה

**הוחלט (בעלים, 22.9):** בהרצת בדיקה הצומת יגיד "הייתי מחייב" — **בלי חיוב אמיתי**.

מההחלטה הזו נגזר הכול. ההרצה היבשה (`engine/dry-run.ts`) מזייפת **רק את מה שעובר דרך
פורט**. ההערה בראש הקובץ: *"הרצה יבשה אינה מימוש שני. היא קוראת לאותו `runWorkflow` ...
רק שלושת הפורטים מוחלפים."*

לכן: **חובה פורט תשלומים.** צומת שיקרא ל-`src/lib/sumit/*` ישירות יחייב כרטיס אמיתי
בכל לחיצה על "הרצת בדיקה".

## §1. עובדות מאומתות

### 1.1 אנטומיית צומת — 5 נקודות נגיעה

נמדד על `action.microsoft_send_email`:

| קובץ | מה נדרש |
|---|---|
| `catalogue/types.ts` | ערך ב-`NODE_TYPES`, טיפוס config, ערך ב-`NODE_REQUIRED_FIELDS` |
| `catalogue/nodes.ts` | `{ type, isTrigger: false }` |
| `catalogue/schemas.ts` | סכימת שדות + ערך ב-`PALETTE_ITEMS` (כולל `outputSchema`) |
| `steps/index.ts` | handler + רישום במפת ה-handlers |
| UI | `normalize-legacy-properties.ts` רק אם משנים שם שדה בעתיד |

**`adapter/to-definition.ts` ו-`catalogue/arm-check.ts` אינם דורשים שינוי** — הראשון
בודק מבנה בלבד ואינו מכיר אף סוג בשמו; השני קורא את `NODE_REQUIRED_FIELDS`.

⚠️ `NODE_TYPES` הוא **חוזה התמדה** (הערה ב-`types.ts`): שינוי שם מייתם כל workflow שמור.

### 1.2 מה ה-handler מקבל

```
StepHandler = (config, ctx) => Promise<NodeExecutionResult>
NodeExecutionResult = { output: unknown; nextPort?: string }
ctx.deps = { guests, alerts, webhook, integrations }   // 4 פורטים, אין תשלומים
```

### 1.3 פלט זמין לצמתים הבאים — בחינם

`resolveConfigTemplates` ב-`activity-runner.ts` פותר `{{nodes.<id>.<path>}}` **במקום
אחד**, לפני שה-handler רץ, מתוך ה-`ExecutionContext` שמכיל את הפלט של כל צומת שהושלם.
ההערה: *"כל שדה של כל סוג צומת מקבל הפניות בחינם, כולל סוגי צמתים שאף אחד עוד לא כתב."*

⇒ מספר מסמך שצומת חיוב יחזיר יהיה זמין מיד לצמתים הבאים, בלי קוד נוסף.

### 1.4 ניתוב שגיאות כבר קיים

`ERROR_POLICIES = ['fail','continue','errorRoute']`. צומת פעולה יכול לצייר ענף שגיאה.
⇒ "אם החיוב נכשל → הודעה לצוות" ניתן לביטוי בלי פיתוח נוסף.

### 1.5 למה לא דרך `IntegrationsPort` (מסלול Microsoft)

ארבע חסימות, כל אחת מספיקה בפני עצמה:

1. `execute()` מחזיר **`{ status: number }` בלבד**. ההערה: *"פנימי למבצע, לעולם לא חוזה
   פלט של workflow"* ⇒ אי אפשר להחזיר מספר מסמך, סכום או קוד שגיאה.
2. `connectionId` הוא שדה חובה. ב-`integration_connections` יש שורה אחת — `microsoft`
   (נבדק ב-DB החי). ל-SUMIT אין שורה.
3. `CredentialPresentation` תומך ב-`bearer` / `header` / `query` בלבד
   (`attachCredential` ב-`authenticated-request.ts`). SUMIT מאמתת ב-`Credentials`
   **בתוך גוף ה-JSON**.
4. פרטי SUMIT יושבים ב-`app_settings` (`sumit_company_id`, `sumit_api_key`), לא
   ב-`integration_connections`.

### 1.6 מנגנון הסודות לא רלוונטי

`{{secrets.X}}` מוגבל ל-`action.webhook` **בלבד** — *"מוגדר לפי צומת, לא לפי שדה"*
(`activity-runner.ts`). צומת SUMIT יקרא את הפרטים דרך הפורט, כמו כל שאר קוד ה-SUMIT.

### 1.7 אילו פעולות יכולות להיות צמתים

8 פונקציות מיוצאות ב-`src/lib/sumit/`. **5 מתאימות:**

| פעולה | סוג | כסף? |
|---|---|---|
| `listSumitHolds` | רשימת תפיסות פתוחות | לא |
| `checkSumitHealth` | בדיקת תקינות חיבור | לא |
| `authorizeHoldSumit` | תפיסת מסגרת (J5) | **תופס** |
| `captureHeldCardSumit` | חיוב על טוקן שמור | **גובה** |
| `creditHeldCardSumit` | זיכוי | **מחזיר** |

**3 אינן מתאימות:**
- `chargeSumit` — דורש `ogToken`, טוקן חד-פעמי שנוצר בדפדפן. ל-workflow אין דפדפן.
- `sumitStatus` — פונקציית פענוח טהורה, לא פעולה.
- `chargeRaw` — כלי האבחון של `/admin/sumit-test`. לא שייך ל-workflow.

## §2. שלבים

### שלב 0 — פורט התשלומים (ארכיטקטורי · דורש אישור נפרד)

**מה:** `PaymentsPort` חמישי ב-`WorkflowEngineDeps` וב-`StepContext.deps`.

מימוש אמיתי ב-worker; **סטאב מקליט בהרצה היבשה**, בדיוק כמו הסטאב של `integrations`
שכותב `NO PROVIDER REQUEST IS MADE`.

**אין צומת חדש בשלב הזה. אפס שינוי התנהגות.**

**למה קודם:** בלי הפורט, כל צומת שייכתב יחייב בהרצת בדיקה. זו היחידה מבין כל ההחלטות
כאן שאי אפשר לתקן אחר כך בלי לשכתב את כל הצמתים.

**אימות:** הסטאב מוכיח בטסט שאף קריאה ל-SUMIT לא יוצאת בהרצה יבשה.

### שלב 1 — שני צמתי קריאה (בלי כסף)

`action.sumit_list_holds` · `action.sumit_health_check`

**למה קודם:** מוכיחים את כל הצינור — פלטה, סכימה, handler, פלט זמין לצמתים הבאים,
ענף שגיאה — **בסיכון כספי אפס**. אם משהו במבנה שגוי, מגלים כאן.

**אימות:** הרצת בדיקה מראה "הייתי קורא"; הרצה אמיתית מחזירה רשימת תפיסות.

### שלב 2 — צומת הזיכוי

`action.sumit_credit`

**למה זה קודם לחיוב:** זיכוי מחזיר כסף ללקוח. טעות כאן עולה לנו, לא לו.

### שלב 3 — שני צמתי הכסף (דורש אישור נפרד)

`action.sumit_authorize_hold` · `action.sumit_capture`

**הכרעות פתוחות שחייבות תשובה לפני כתיבה:**

1. **מאיפה הצומת לוקח את הכרטיס?** מזהה קמפיין בשדה, והטוקן נשלף בשרת (כמו הבורר
   שנבנה ב-`/admin/sumit-test`)? או טוקן בשדה? ⚠️ טוקן בשדה = טוקן תשלום בתוך
   דיאגרמה ב-jsonb, גלוי בעורך וביצוא.
2. **האם צומת חיוב יכול לעקוף את `close_charge_enabled`?** היום הוא המתג הראשי לכסף
   אמיתי. workflow שגובה בלעדיו הוא דלת צדדית.
3. **מניעת כפילות.** ה-ledger מונע הרצה כפולה של אותו צומת באותו run. הוא **לא** מונע
   שני runs שגובים את אותו קמפיין.
